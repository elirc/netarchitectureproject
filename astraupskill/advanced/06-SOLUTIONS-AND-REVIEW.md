# Separate solutions: distinguish the proof from its surroundings

Use these answers to review reasoning, not to replace the first attempt. A successful engineering explanation should tell a reviewer where rejection occurs, what has already happened, and which observation would falsify the claim.

**MA-01 through MA-03:** current success regressions check requested start and end on the aggregate passed to the repository or returned as the existing meeting. Invalid create cases assert a domain exception and no `AddAsync`. The change path reads its meeting first, then evaluates the factory argument. Invalid term construction prevents entry into `ChangeMainAttributes`. This supports term preservation for the covered invalid interval; complete aggregate immutability, HTTP formatting, and database rollback require additional evidence. The diagram should show request end mapping to factory end in both handlers, not merely a valid value-object unit test.

**MA-04:** the invariant accepts every strictly positive interval, including one tick, overnight, and long intervals. Equal and reversed inputs reject. A different maximum duration or local-calendar restriction cannot be inferred. The repository-add assertion concerns the create path. The change test must inspect the same aggregate instance supplied by its repository substitute; inspecting a separately constructed object proves nothing about the handler's mutation.

**MA-05 and MA-06:** compare an explicit before/after projection that includes mutable properties, identity and audit values, nested collection contents, and domain events. Snapshot lists into independent structures. Include `_changeDate` and `_changeMemberId`, which are easy to miss if attention stays on title and term. Also account for cancellation fields and creation metadata even though the intended change should not touch them. A defective implementation that assigns a new title and audit timestamp before a later rule throws must fail the proposed criterion. Checking only `_term` is not enough for a title-rule rejection.

**MA-07 and MA-08:** the positive one-tick row establishes strictness without inventing a minimum duration. Equality distinguishes `<=` from `<`. In the mapping mutation, compilation is supposed to succeed; the valid-request path fails because the adapter loses the requested end. A shifted-end mutation can still produce a valid interval, so only asserting absence of exceptions would miss it. Assert the exact requested boundary as well as rule acceptance. The source-bound runner copies real domain files but its mapping adapter is not the production handler, so retain the actual handler regression as separate evidence.

**MA-09:** reflection errors belong to setup or invocation until the handler's returned task actually executes the business logic. Keep diagnostic exception assertions distinct from business-rule assertions. When a method throws before returning a task, reflection may wrap the exception; when the task faults, await observes that fault. Avoid a blanket catch that treats either path as an expected invalid-title result. Such a catch would turn a misspelled handler name into a green domain test.

**MA-10 through MA-12:** one acceptable design is a reusable title rule invoked by both aggregate creation and `ChangeMainAttributes` before any assignments. Validate null and trimmed length deliberately. Store either original or trimmed text according to the written contract, and test that choice. A rejected change should preserve every projected field and the exact event sequence. A valid change may append the expected change event and update change metadata while leaving creation/identity fields alone. UI feedback and HTTP mapping remain separate contracts; domain validation does not automatically supply accessible form behavior or a particular response status.

This extension is intentionally proposed work. The documentation does not add a title rule to the application, alter existing handler signatures, or claim that the expanded all-fields tests have already been implemented in the production test suite.
